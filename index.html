My Role

내가 맡은 부분

3명이 함께 만든 프로젝트입니다. 제가 직접 설계하고 구현한 부분과 팀원 작업을 구분했습니다.

직접 담당

  • AI 해석 API 설계와 구현 (Claude로 프로토타입 → Gemini로 전환)
  • 프롬프트 설계, 구조화 출력, 할루시네이션 방지 규칙

Design Decisions

설계 결정 세 가지

A

모든 문장을 AI에 보내지 않는다

팀원이 만든 규칙 파서가 먼저 해석하고, 실패한 문장만 Gemini로 넘깁니다. AI 호출 비용을 아끼고 응답이 빨라지며, API 키가 없어도 기본 기능은 동작합니다. 저는 AI 쪽 경로와 "등록인지 취소인지 먼저 판단하는" 단계를 붙였습니다. 해석 경로를 잘못 타서 엉뚱한 일정이 지워지는 일을 막기 위해서입니다.

B

모르는 말은 한 번 묻고 기억한다

"종숲"처럼 친구끼리만 쓰는 줄임말은 인터넷 어디에도 없어서 AI가 알 수 없습니다. 그래서 처음 한 번만 뜻을 물어보고 {별명, 이름, 주소, 카테고리}로 저장합니다. 다음부터는 "종숲 ㄱ"만 써도 장소와 카테고리가 자동으로 붙습니다. 비슷한 패턴("잠숲")은 AI가 추측만 하고, 확정은 항상 사용자가 합니다.

C

AI 응답을 그대로 믿지 않는다

JSON 스키마로 출력 형식을 강제해도 내용까지 맞는 건 아닙니다. 서버에서 응답을 한 번 더 검사해서, 개인 사전과 정확히 일치하는 별명이 있으면 AI 답보다 사전을 우선합니다.

Troubleshooting

배포 하루 동안 연달아 터진 문제 네 가지

Claude API로 만든 해석 기능을 무료로 운영하려고 Gemini로 옮긴 날(9월 17일) 생긴 일입니다. 하나를 고치면 다음 문제가 드러나는 식이었고, 무료 티어의 한계는 결국 개발 중 유료 등급으로 전환해 해결했습니다.

CASE 1 · FUNCTION_INVOCATION_FAILED

서버 함수가 요청을 보내기도 전에 죽음

증상
AI 해석 요청이 전부 실패. 실행 시간이 몇 ms밖에 안 됨
단서
Vercel 로그의 외부 API 호출 목록이 비어 있음 → 네트워크 요청 자체를 못 보냄
원인
Gemini SDK는 Node 20 이상이 필요한데 버전 지정이 없어 구버전 런타임에서 실행됨
해결
engines.node: ">=20" 명시. 방어용으로 바꿨던 import 경로가 오히려 더 크게 깨뜨린 것도 발견해 되돌림

배운 점 실제 배포 환경에서 확인하기 전에는 "안전하게" 넣은 수정도 위험할 수 있다.

CASE 2 · 404 NOT FOUND

쓰던 모델이 사라짐

증상
크래시를 고치자 이번엔 Google API가 404를 반환
단서
에러 원문을 응답에 잠깐 노출해([DEBUG], 확인 후 제거) 정확한 메시지 확인
원인
gemini-2.5-flash가 신규 계정에 더 이상 제공되지 않음
해결
에러 메시지가 안내한 후속 모델로 교체
CASE 3 · 503 / 429 / 깨진 한글

무료 티어에서 쓸 만한 모델 고르기

모델마다 다른 방식으로 실패해서, 운영 환경에서 직접 돌려 보며 비교했습니다.

모델문제결과
gemini-3.8-flash최신 모델이라 요청이 몰려 절반 가까이 503(과부하)탈락
gemini-3.5-flash하루 20건 한도라 금방 429(한도 초과)탈락
gemini-3.1-flash-lite한도는 넉넉하지만 한글이 깨지고 없는 장소를 지어냄탈락
gemini-3.6-flash품질과 가용성의 균형이 가장 안정적채택

결론 모델을 바꿔도 무료 티어에서는 503·429를 완전히 없앨 수 없었습니다. 개발 중 Gemini 유료 등급으로 전환해 해결했습니다.

CASE 4 · HALLUCINATION

"모르면 비워 둬"가 통하지 않음

증상
텍스트에 없는 "홍대"를 장소로 지어냄. 반대로 "종숲"은 장소인지조차 몰라서 "물어보기" 흐름이 아예 시작되지 않음
원인
"하지 마라"는 지시만으로는 모델이 어떤 단어가 장소 후보인지 판단할 기준이 없음
해결
구체적인 반례(few-shot)와 "날짜·시간·행동이 아닌 짧은 명사는 장소 후보로 본다"는 규칙을 프롬프트에 추가

이후로는 잘못 해석된 문장을 원인별로 나눠 반영했습니다. 처음 보는 줄임말은 사용자 확인을 거쳐 개인 사전에 저장하고, 반복되는 오해석("종숲·구로숲"을 장소로 못 봄, "병원에서 업무 미팅"을 건강으로 분류)은 프롬프트 규칙으로 추가했습니다. 실제로 틀렸던 사례가 그대로 규칙이 된 셈입니다.

배운 점 약한 모델일수록 금지 지시보다 "이럴 땐 이렇게"라는 예시가 잘 통한다.

How I Built It With AI

QA 자동화 엔지니어가 AI와 함께 만든 방식

저는 QA 자동화 엔지니어로 일하며 Python 자동화 코드는 써 봤지만, 웹 서비스를 직접 만들어 배포한 건 이번이 처음입니다. 그래서 Claude Code에 코드를 맡기기만 하지 않고, 기획은 제가 정하고 기술 선택과 구현은 AI와 함께 결정하되, 제가 이해한 만큼만 진행하는 방식으로 작업했습니다.

  1. 기획만들 기능과 사용자 경험을 먼저 정함내가 결정
  2. 기술 결정기획에 맞는 구현 방법과 기술을 AI에게 선택지로 받고 장단점을 비교해 고름AI가 제안, 내가 선택
  3. 구현정한 방향대로 AI가 코드를 작성AI가 구현
  4. 이해와 검증동작 원리를 설명받고 배포 환경에서 직접 확인함께

이 방식을 매번 말로 요청하지 않도록, AI가 따를 학습 규칙을 미리 적어 두었습니다.

· 설계와 방향은 사용자가 먼저 결정하게 한다. 선택지와 장단점을 제시한다.
· 코드를 한 번에 다 짜지 않는다. 단계별로 나누고 각 단계를 설명한다.
· 단계가 끝날 때마다 사용자가 이해했는지 확인한 뒤 다음으로 넘어간다.
· 커밋 메시지는 무엇을, 왜 바꿨는지 한국어로 쉽게 쓴다.

그 결과 위 트러블슈팅 같은 문제를 만났을 때 AI가 고쳐 주기만 기다리지 않고, 로그를 보고 원인을 좁혀 가는 과정을 직접 주도할 수 있었습니다.
